Mental model

It's three systems in a trench coat

Every macro tool — yours, SteelSeries, DS4Windows, AutoHotkey — is really just these three parts. Build them in order and it's never as big as it looks.

01 · Capture

Watch armed keys only

While a macro is enabled, the app watches for its trigger key(s) and ignores everything else — see Safety & trust below.

Why it matters: to bind a macro to a key and stop it typing normally, the hook must swallow the original press.

02 · Execute

Replay the sequence

Fire the recorded events with correct timing — keystrokes, text, mouse, delays, launch apps.

This is the "software injection" part. It's the same path all three reference tools use.

03 · Interface

See & edit macros

A visual keyboard to assign binds and a timeline to record and edit — plus JSON storage and a tray toggle.

The biggest chunk of work, and the difference between "polished" and "Wootomation".

Safety & trust

Designed to be obviously not a keylogger

A macro tool has to watch the keyboard — the same thing a keylogger does. So the design earns trust on purpose, and stays auditable.

Gated

No hook unless armed

The global hook is installed only while at least one macro is enabled, and removed the instant you toggle everything off. Idle app = nothing watching.

Allowlist

Only armed keys, never stored

While active, it checks each event against the small set of keys with an enabled binding and returns immediately for anything else. Keystrokes are never buffered, logged, or written to disk.

Narrowest API

Prefer RegisterHotKey

For a macro that just fires on a key press, Win32 RegisterHotKey makes the OS notify you for that one key only. The low-level hook is the fallback for while-held, key-up, suppression, and analog.

Auditable

Open source

All of the above is verifiable by anyone reading the code — the strongest trust signal there is.

Technical note: a Windows low-level keyboard hook (WH_KEYBOARD_LL) is invoked for every key by OS design — you can't ask Windows to call you for only one key. The trust guarantee comes from what the callback does (filter to armed keys, never record) and when it's installed (only while a macro is enabled), not from the hook selectively not seeing keys. RegisterHotKey is the one API that literally fires for just the registered key.

Timing & precision

Hitting 1 ms without drift

Macros need a 1 ms floor and intervals that stay accurate over minutes. Windows fights you: default timer granularity is ~15.6 ms, and naive sleep(interval) loops drift because every sleep overshoots a little and the errors pile up.

The core trick (from Blur-AutoClicker's engine): don't sleep for interval each cycle — schedule against a fixed grid of absolute deadlines. Advance nextFire += interval relative to the previous target (never to "now"), then wait only until that absolute instant. If one cycle runs long, the next automatically waits less to catch up — so the average interval stays exactly on target. That is the "measure how far off it was, correct the next one" mechanism; anchoring to absolute time does it for free.
using System.Diagnostics;

long freq     = Stopwatch.Frequency;
long interval = freq / 1000;            // 1 ms, in Stopwatch ticks
long nextFire = Stopwatch.GetTimestamp();

while (running)
{
    FireMacroStep();                    // press / release / delay

    nextFire += interval;                // anchor to the ideal grid — NOT to "now"

    long remaining = nextFire - Stopwatch.GetTimestamp();
    if (remaining > 0)
        SleepThenSpin(remaining);       // coarse sleep, then spin the last ~1 ms
    // remaining <= 0 → we're behind: fire now and catch up
}
Resolution

timeBeginPeriod(1)

Raise the system timer to 1 ms while a macro runs; restore on stop (IDisposable guard). Only while firing — it's system-wide.

Last millisecond

Sleep, then spin

Coarse-sleep the bulk, then busy-spin (Thread.SpinWait) the final ~1 ms for tight accuracy. Costs CPU — gate behind a high-precision toggle.

Guardrails

Clamp & interrupt

Clamp every delay to max(1, x) ms; wait in small ticks checking the stop flag so toggling off stays responsive.

This timing machinery is entirely OS/CPU-level — nothing to do with the Wooting, and identical on any keyboard. System.Threading.PeriodicTimer is a simpler, coarser alternative; the Stopwatch + spin loop is what reliably hits 1 ms.

Performance & footprint

Lightweight, and no stutter in games

It'll run during games where jitter matters, so the whole design targets low CPU/RAM and zero random freezes.

Idle

≈ free, or closed

A normal app, not a service — open it for macros, close it and nothing lingers. While open, the hook is gated off until a macro is armed.

Hot loop

No GC stutter

The engine runs on its own high-priority thread, never the UI thread, and allocates nothing per cycle — GC pauses are the classic cause of random freezes.

Hook

Tiny callback

A slow low-level hook adds system-wide input lag and can be dropped by Windows, so the callback just checks the armed keys and signals the engine.

Built for rapid on-demand triggering: the engine thread stays alive and waiting and the hot path is pre-warmed (ReadyToRun), so firing a macro several times a second feels lag-free even on the first fire. The sub-ms spin-wait costs a core, so it's behind the high-precision toggle and runs only during an active macro. Honest note: any host-side tool adds a little latency vs. raw hardware — a tight engine keeps it minimal and, more importantly, consistent.

Analog features · Phase 2

The Wooting-only superpower

Only possible on a Wooting (via the Analog SDK), all opt-in and off by default — an optional module, not a fork.

Main idea

Multi-point actuation

One key fires different actions at different press depths — a light press does X, a full press does Y. Like onboard DKS, but host-side so it can fire full macros.

Trigger

Depth threshold

Fire a macro when a key crosses a chosen depth (e.g. 50%).

Continuous

Depth → analog output

Map how far a key is pressed to a smooth value: mouse speed, scroll, a gamepad axis, volume. The genuinely unique analog-to-analog case.

Gating

Hold past a depth

A while-held macro repeats only while the key is pressed beyond a set depth.

Reading analog means polling the SDK on a loop, which costs some CPU — another reason it's a dormant, optional module unless you're using it.

First step

What phase 1 actually looks like

A console app: press Caps Lock, get text typed. Runs on your Mac tonight (grant Accessibility), then the exact logic moves into WPF on your PC.

using SharpHook;
using SharpHook.Native;

var sim  = new EventSimulator();
var hook = new SimpleGlobalHook();

hook.KeyPressed += (s, e) =>
{
    if (e.Data.KeyCode == KeyCode.VcCapsLock)
    {
        e.SuppressEvent = true;              // swallow the real key (Windows)
        sim.SimulateTextEntry("gg ez");      // fire the macro
    }
};

hook.Run();   // listen for global key events

Treat it as the shape, not gospel — check SharpHook's current API for exact names. Every line here carries straight into the real app.

Before you build

Four things worth knowing

!

The keyboard can't do this itself.

The 60HE offers DKS, Mod Tap, Toggle Key, remaps and 4 onboard profiles — but those are fixed depth-rules, not recorded, timed, repeatable macros. Those must live in your app.

!

SteelSeries & DS4Windows are software too.

Same injection path as AutoHotkey. The thing you liked about them over AHK is the GUI — which is exactly what you're building.

!

Anti-cheat can flag injected input.

Global hooks + synthesized input trip some game anti-cheats. Check the ToS of any game you'd use it alongside.

!

Prototype on Mac, ship on Windows.

The engine (SharpHook) runs on your Mac for testing now. WPF is Windows-only, so the GUI and final build happen at your PC.
