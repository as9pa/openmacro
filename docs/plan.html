The premise

Keyboard software rarely does macros well — the Wooting's own Wootomation is basic, and keyboard firmware generally has no macro engine at all. So this is a host-side desktop app that does what SteelSeries Engine and DS4Windows do: a clean GUI to record, edit, and fire macro sequences. Works with any keyboard; a Wooting unlocks analog features on top.

Everything below is decided but unbuilt. This log is the spec — the code starts at Phase 1.

01

Decisions

[LOCKED]

Native Windows app

Open it when you want macros (not an always-on service); minimize to tray to arm/disarm, close it and nothing lingers.

[LOCKED]

C# / .NET + WPF

Windows-native. Hooks, input, and the Wooting SDK are all short interop calls; WPF gives a real GUI.

[LOCKED]

Host-side injection

The same path SteelSeries, DS4Windows, and AutoHotkey use. It was always software — the difference is the GUI.

[LOCKED]

One codebase → two builds

A Core installer and a Wooting installer from the same source — build flavors, not a fork.

[FEATURE]

Record · edit · replay

Recorder with an editable timeline, add/edit delays, and playback modes: Once · While-held · Toggle.

[LOCKED]

Graceful stop

On stop, finish the current cycle cleanly (immediate-stop is an option). Either way, never leave a key held down.

[LOCKED]

Clean, minimal UI

Modern but restrained — never overloaded (Blur-AutoClicker is too dense). Advanced options tucked away until needed.

[PHASE 2]

Analog depth features

Optional module, active only on a Wooting: different actions at different press depths, and more. No other keyboard can do it.

02

How it works

Every macro tool — yours, SteelSeries, AutoHotkey — is really just three parts. Build them in order.

A

Capture

While a macro is armed, a background hook watches for its trigger key(s) and ignores the rest.To bind a macro to a key and stop it typing normally, the hook must swallow the original press.

B

Execute

Replay the recorded events with correct timing — keystrokes, text, mouse, delays, launch apps.This is the "software injection" part — the same path all the reference tools use.

C

Interface

A visual keyboard to assign binds and a timeline to record/edit, plus JSON storage and a tray toggle.The biggest chunk of work — and the difference between "polished" and "Wootomation".

03

Safety & trust

A macro tool watches the keyboard — the same thing a keylogger does. So it's designed to be obviously not one, and stays auditable.

›

No hook unless armed

The global hook is installed only while a macro is enabled, and torn down the instant you disable everything. Idle = nothing watching.

›

Allowlist, never stored

While active it checks each event against the armed-key set and returns immediately otherwise. Keystrokes are never buffered, logged, or written to disk.

›

Narrowest API

For a simple fire-on-press bind, RegisterHotKey makes the OS notify you for that one key only. The low-level hook is the fallback.

›

Open source

All of the above is verifiable by anyone reading the code.

Note: a Windows low-level hook (WH_KEYBOARD_LL) sees every key by OS design — you can't scope it to one. The guarantee comes from what the callback does (filter + never record) and when it's installed (only while armed).
04

Data model

Get these shapes right and the rest is UI.

Macro       = ordered list of MacroEvent

MacroEvent  = KeyDown(key) | KeyUp(key) | Delay(ms)
            | Text("gg ez") | LaunchApp(path) | MouseClick(btn)

Binding     = Trigger + Macro + PlaybackMode
              Trigger      = a key    // Phase 2: key + depth threshold
              PlaybackMode = Once | WhileHeld | Toggle

Profile     = list of Bindings + optional "match this app" rule
Config      = list of Profiles       // → JSON in %AppData%

06

Timing

1 ms floor, accurate over minutes. Windows fights you: default granularity is ~15.6 ms, and naive sleep(interval) loops drift as errors pile up.

The trick (from Blur-AutoClicker's engine): don't sleep for interval — schedule against a fixed grid of absolute deadlines. Advance nextFire += interval from the previous target (never "now"), then wait only until that instant. Overshoot in one cycle is absorbed by the next, so the average stays exact.
long interval = Stopwatch.Frequency / 1000;  // 1 ms in ticks
long nextFire = Stopwatch.GetTimestamp();

while (running) {
    FireMacroStep();
    nextFire += interval;                    // anchor to the grid, NOT to "now"
    long left = nextFire - Stopwatch.GetTimestamp();
    if (left > 0) SleepThenSpin(left);       // coarse sleep, spin last ~1 ms
}
›

timeBeginPeriod(1)

Raise system timer resolution to 1 ms while running; restore on stop. System-wide, so only while firing.

›

Sleep, then spin

Coarse-sleep the bulk, busy-spin the last millisecond. Costs CPU — behind a high-precision toggle.

›

Clamp & interrupt

Clamp every delay to max(1, x) ms; wait in small ticks so a stop is instant.

07

Performance

It runs during games where jitter matters — so the whole design targets low CPU/RAM and zero random freezes.

›

Idle ≈ free, or closed

A normal app, not a service — open it for macros, close it and nothing lingers. Hook gated off until armed.

›

No GC stutter

Engine on its own high-priority thread, never the UI thread, allocating nothing per cycle — GC pauses are the classic freeze cause.

›

Tiny hook callback

A slow low-level hook adds system-wide input lag and can be dropped by Windows — so it just checks armed keys and signals the engine.

›

Instant, even first fire

Firing a macro several times a second stays lag-free: the engine thread waits ready, and the hot path is pre-warmed (ReadyToRun) so cold JIT never bites.

Any host-side tool adds a little latency vs. raw hardware — a tight engine keeps it minimal and, more importantly, consistent.

08

Analog · Phase 2

Only on a Wooting (via the Analog SDK), all opt-in and off by default — an optional module, not a fork.

1

Multi-point actuation — the main idea

One key fires different actions at different press depths (light = X, full = Y). Like onboard DKS, but host-side so it can fire full macros.

2

Depth-threshold trigger

Fire a macro when a key crosses a chosen depth, e.g. 50%.

3

Depth → continuous output

Map press depth to a smooth value: mouse speed, scroll, a gamepad axis, volume. The genuinely unique analog-to-analog case.

4

Hold past a depth

A while-held macro repeats only while pressed beyond a set depth.

Reading analog means polling the SDK on a loop — a CPU cost, so it's dormant unless you're using it.

10

Phase 1, concretely

A console app: press Caps Lock, get text typed. Runs on macOS tonight (grant Accessibility); the logic moves straight into WPF later.

using SharpHook;
using SharpHook.Native;

var sim  = new EventSimulator();
var hook = new SimpleGlobalHook();

hook.KeyPressed += (s, e) => {
    if (e.Data.KeyCode == KeyCode.VcCapsLock) {
        e.SuppressEvent = true;              // swallow the real key
        sim.SimulateTextEntry("gg ez");      // fire the macro
    }
};
hook.Run();
